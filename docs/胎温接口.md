# CANB 胎温接口

本文确认 `DATA_COLLECTION_INTEGRAL` 采集节点发送的四轮 MLX90640 胎温摘要。字段定义以 [`Vehicle_CanB.dbc`](../can/Vehicle_CanB.dbc) 为准。

## 1. 总线和轮位

- 总线：整车 CANB，500 kbit/s。
- 帧格式：11 位标准帧，DLC=8。
- 发送节点：`DATA_COLLECTION_INTEGRAL`。
- 接收节点：`Display`、`WirelessGateway`、`VEHICLE_LOGGER`。

| 传感器索引 | TCA9548A 通道 | 轮位 | CAN ID | DBC 报文名 |
| ---: | ---: | --- | --- | --- |
| 0 | 0 | 右前 FR | `0x72` | `MLX90640_TireTemperature_FR` |
| 1 | 1 | 左前 FL | `0x71` | `MLX90640_TireTemperature_FL` |
| 2 | 2 | 左后 RL | `0x73` | `MLX90640_TireTemperature_RL` |
| 3 | 3 | 右后 RR | `0x74` | `MLX90640_TireTemperature_RR` |

该映射按采集固件的实际 CAN 发送路径确认。接收端应按 CAN ID 判断轮位，不应按报文到达顺序推断轮位。

## 2. 区域顺序和温度计算

MLX90640 图像为 24 行 × 32 列。采集端对每个轮位计算四个水平带的算术平均值，每个带均包含全部 32 列：

| 带编号 | 图像行 | CAN 字节 | 字段 |
| ---: | --- | --- | --- |
| Band0 | 0..5 | Byte0、Byte1 | `Band0_Integer`、`Band0_Fraction` |
| Band1 | 6..11 | Byte2、Byte3 | `Band1_Integer`、`Band1_Fraction` |
| Band2 | 12..17 | Byte4、Byte5 | `Band2_Integer`、`Band2_Fraction` |
| Band3 | 18..23 | Byte6、Byte7 | `Band3_Integer`、`Band3_Fraction` |

顺序固定为传感器图像从上到下。它不是四象限顺序，也不是 16 个独立测温点。

每个带使用两个无符号字节。偶数字节为整数摄氏度，后一个奇数字节为百分之一摄氏度：

```text
temperature_degC = Integer + Fraction × 0.01
```

例如 `17 2D` 表示 `23.45 °C`。采集端先把区域平均温度四舍五入为 `0.01 °C`，负值编码为 `0.00 °C`。协议没有单独的无效值；接收端需要结合报文超时判断数据是否有效。

## 3. 发送条件和超时

采集任务每 200 ms 轮询一个传感器，因此同一轮位约每 800 ms 被访问一次。只有收齐 MLX90640 的两个子页并形成完整温度图后才发送对应 CAN 帧；传感器配置为 0.5 Hz，实际帧间隔会受子页就绪时间和采集重试影响，因此本接口按“完整图像就绪时触发”处理，不声明固定 `GenMsgCycleTime`。

接收端建议在超过 5 s 未收到某轮位报文时将该轮位标为超时。超时阈值是接收策略，不改变 DBC 中的信号值。

## 4. 兼容性

此前临时 DBC 使用全局编号 `TireTemp01..16`，并把四个值描述为轮胎横向测点。实际固件发送的是每个传感器图像的四个水平带平均值。本次将报文名和信号名改为轮位与 `Band0..Band3`，同时确认 `0x71=FL`、`0x72=FR`、`0x73=RL`、`0x74=RR`。ID、DLC、字节位置、比例、发送节点和接收节点保持不变。
