# 整车接口协作与维护

本文件规定仓库归属、审核、发布和交接。接口修改的具体操作要求见 [`CONTRIBUTING.md`](../CONTRIBUTING.md)，未完成事项见 [`迁移与待确认项.md`](迁移与待确认项.md)。

## 1. 仓库归属

本仓库归属 `BITFSAE` GitHub Organization，是整车 CAN DBC 和遥测 Proto 的中央来源。各项目负责实现和使用接口，不再维护另一份“正式协议”。

现阶段只维护公开接口仓库。真实凭据和生产部署配置由对应系统单独保管。

## 2. 文件职责

- `can/`：正式 DBC。
- `telemetry/`：正式 Proto、Nanopb options 和遥测说明。
- `docs/CAN_ID分配.md`：ID 归属索引。
- `docs/CAN1接口.md`、`docs/CANB接口.md`：DBC 无法完整表达的周期、超时、兼容和应答规则。
- `docs/ECU_SOP实现确认.md`：ECU 最终 SOP 接收、限制、扭矩、周期和确认策略确认模板。
- `docs/迁移与待确认项.md`：尚未确认的接口、周期、优先级和验证。
- `CHANGELOG.md`：已完成变更、兼容影响和待办。
- `CONTRIBUTING.md`：提交接口变更的检查项。

字段布局以 DBC、Proto 和 options 为准。Markdown 不重复维护整份信号表，只补充使用接口所需的规则。

## 3. 节点确认责任

接口的“已确认”以节点负责人书面记录为准，不能只根据 DBC 存在、旧文档或“已经接到遥测”判断。**节点不仅要提交 DBC，还要提供对应报文说明文档，说明字段、单位、比例、有效范围、周期、发送/接收节点和异常处理。**

当前周期、触发条件和处理优先级均为暂定值，节点应结合实际模型、接收端需求和 CAN 容量给出最终值；如果现有值不合理，应提出修改方案。

建议各节点负责人至少确认以下内容：

| 节点 | 需要负责确认的报文 | 需要补充的说明 |
| --- | --- | --- |
| ECU | `0x305`、`0x310`（接收）、`0x502..0x509`、`0x4A0/0x4A3`（接收）、`0x4A4`（发送） | `0x305`、`0x502..0x509`、`0x4A4`；SOP 策略和合理性 |
| Display/HMI/遥测 | `0x050`、`0x060..0x066`、`0x067..0x06A`、`0x301`、`0x310`（发送） | GPS/IMU/模式请求；周期和优先级 |
| 胎温采集模块 | `0x071..0x074` 胎温 | 轮位映射、温度公式、周期和优先级 |
| PDM | `0x5A0/0x5A1` | 周期、无效值、电流方向和累计电量起点 |
| FanController | `0x5A2..0x5A9/0x5AE` | 控制逻辑、CRC、应答、功率仲裁、两档标定和故障安全参数 |
| BMS | `0x5AA..0x5AD`、`0x186250F4/0x186E50F4` | 电池箱风扇控制、两档功率限值、状态位和保存流程 |
| 方向盘 | `0x700`、`0x784` | 模式枚举、触发条件和冗余发送逻辑 |
| 赛会设备 | `0x430/0x521/0x522/0x526/0x528` | 版本、MUX、状态位、功率/Wh 是否发送 |

各节点确认时应重点判断：发送周期是否恰当、处理优先级是否过高、是否存在误触发 0 动力或无关断动力、恢复策略是否合理。

## 4. 维护角色

### Organization Owner

至少保留 2 名 Owner，负责账号恢复、成员权限和仓库连续性。Owner 不需要参与每次接口审核。

### 当前维护者

- 管理 Issue、PR、Release 和访问权限；
- 检查接口完整性、兼容影响和验证证据；
- 交接前带下一任完成一次真实 PR 和 Release。

### 下一任维护者

- 先加入维护 Team 并参与审核；
- 能独立完成分支、校验、PR、合并和发布后再接任；
- 接任时复核 Owner、Team、CODEOWNERS 和外部协作者。

## 5. 审核和分支保护

`main` 只接收通过自动校验的 Pull Request，禁止强制推送和删除。普通接口改动至少需要 1 名维护者审核。

下列改动需要 2 人复核；只有一名维护者时，由受影响系统负责人参与并在 PR 中确认：

- 不兼容修改；
- 安全相关控制报文；
- 同时影响多个系统的修改；
- 周期、优先级、触发条件或策略发生修改。

合并使用 Squash Merge，并在合并后删除功能分支。新提交应使旧审核失效，未解决的审核对话不得合并。

## 6. 版本和下游使用

- `MAJOR`：不兼容修改。
- `MINOR`：向后兼容地增加报文、字段或功能。
- `PATCH`：不改变线缆协议的文档、注释或校正。

发布稳定版本时创建 Tag 和 Release。下游项目固定到 Release 或 Commit，并在自己的文档或构建配置中记录版本；不直接跟随 `main`。

## 7. 发布检查

1. 自动校验全部通过。
2. `CHANGELOG.md` 写明版本、日期和兼容影响。
3. 不兼容修改提供迁移步骤。
4. [`迁移与待确认项.md`](迁移与待确认项.md) 中没有 `v1.0.0` 发布阻断项。
5. 各节点已提交报文说明文档，而非只有 DBC。
6. 已确认周期、优先级和策略没有明显误触发风险。
7. 创建受保护 Tag 和 Release 说明。
8. 通知受影响项目更新固定版本。

## 8. 交接检查

1. 下一任完成一次真实 PR 和 Release 演练。
2. 复核 Owner、Team、CODEOWNERS 和 Secrets 访问者。
3. 轮换需要移交的凭据，清理离队成员权限。
4. 未完成事项登记到 Issue、`CHANGELOG.md` 或 [`迁移与待确认项.md`](迁移与待确认项.md)。

当前发布前工作以 [`CHANGELOG.md`](../CHANGELOG.md) 的“未发布/待办”为准。
